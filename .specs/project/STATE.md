## Lições

- **NestJS + Vitest: injeção de dependência implícita por tipo não funciona.** O Vitest transpila via esbuild, que não emite `design:paramtypes` (só o `tsc` real emite, via `emitDecoratorMetadata`). Todo construtor de controller/provider precisa de `@Inject(Token)` explícito — nunca só o tipo do parâmetro. Descoberto em T11, virou convenção documentada em `TESTING.md`.
- **`current_setting(nome, true)` pode devolver `''` em vez de `NULL`** numa conexão que já teve o GUC customizado tocado antes na mesma sessão (mesmo depois do fim da transação que o setou com `is_local`). Como o pool reaproveita conexões, uma policy de RLS que compara direto com `::uuid` pode quebrar em vez de simplesmente filtrar. Corrigido envolvendo em `nullif(current_setting(...), '')::uuid`. Descoberto em T5.
- **`argon2.hash()` não trata chave com valor `undefined` explícito como "use o default".** Passar `{ memoryCost: options.memoryCost }` quando `options.memoryCost` é `undefined` quebra a validação interna da lib. É preciso omitir a chave inteira, não só deixar o valor `undefined`. Descoberto em T14.
- **Projetos distintos do Vitest rodam concorrentes por padrão**, mesmo com `fileParallelism: false` (que só serializa arquivos *dentro* de um projeto). Como `integration` e `e2e` sobem Postgres via Testcontainers cada um, isso pode saturar a memória do Docker Desktop. `pnpm test` roda os três projetos em sequência por isso. Descoberto em T17.
- **Docker Compose cacheia o objeto de secret no daemon quando usa driver `file:`.** Trocar o conteúdo do arquivo host depois que o container já foi criado não atualiza o secret montado — nem `up -d` nem `--force-recreate` bastam. É preciso `docker compose down` (remove os secrets) antes de subir de novo. Descoberto testando a T5 ao vivo.
- **`drizzle-kit` 0.28 não gera `FORCE ROW LEVEL SECURITY`** — só `ENABLE`. Toda tabela nova sob RLS precisa da linha `ALTER TABLE ... FORCE ROW LEVEL SECURITY;` acrescentada à mão na migração gerada, senão o teste de introspecção reprova nomeando a tabela. Confirmado de novo na T9 (já era conhecido do M0, T9 do M0).
- **Teste que conta "o total de X no banco inteiro" quebra quando o schema cresce de forma legítima.** `migrate.int.test.ts` contava todas as foreign keys do banco esperando um número fixo; a chegada de `connector_bindings` (com FK de verdade) quebrou um teste que não tinha nada a ver com ela. Corrigido restringindo a query às tabelas que o teste queria provar. Lição: teste de contagem global é frágil — prefira escopar ao que o teste realmente afirma. Descoberto na T9.
- **`pnpm run test:int` completo pode falhar por esgotamento de recursos, não por regressão.** Docker Desktop com 3.8 GB / 2 CPUs, dividido com outros contêineres do usuário (mongodb, mongo-express), começou a derrubar Testcontainers por timeout/OOM quando o número de suítes de integração cresceu com o M1. Nenhum container órfão fica pra trás — é contenção real de recurso. Confirmar rodando os arquivos afetados em lotes pequenos antes de reportar regressão. Descoberto na T11.
- **Teste que varre todo tenant do banco precisa isolar tenant E recurso externo (KEK) por teste, não só um dos dois.** `kek-rotate.int.test.ts` criava um tenant novo por teste, mas reusava a mesma base de dados sem truncar `connector_connections`/`tenants` entre testes — sobra de conexão de um teste era "achada" pelo próximo, selada sob uma KEK que o `afterEach` já tinha apagado do disco, e a rotação quebrava com erro de autenticação do GCM. Corrigido truncando as duas tabelas em `afterEach`. Descoberto na T8.
- **Zod 4 valida UUID pela RFC de verdade.** O fixture `11111111-1111-1111-1111-111111111111` passava no Zod 3 e é recusado no Zod 4: o nibble de versão e o de variante não batem com a RFC 9562. IDs reais (v7, do `newId`) passam normalmente — o teste é que estava frouxo. Ao escrever fixture de UUID, use um v7 de verdade. Descoberto na migração da T1.
- **`import.meta` não compila sob o `module: CommonJS` do projeto.** Teste que precisa do próprio caminho resolve a partir de `process.cwd()` (o Vitest roda da raiz do monorepo). Descoberto na T1.
- **`tsx` (esbuild) resolve `tsconfig.json` com `extends` relativo subindo diretórios** — então o Dockerfile precisa copiar `tsconfig.base.json` da raiz, não só o pacote sendo buildado, senão decorators quebram silenciosamente (mesma causa-raiz do primeiro item, manifestada de outro jeito). Descoberto em T23.
- **`fireEvent.change` num `<select>` do Testing Library não seleciona um valor que não existe como `<option>`.** `event.target.value` fica vazio (não o valor pedido) se nenhuma opção corresponder — silencioso, sem erro, só um teste que nunca dispara o `onChange` esperado. Ao testar um `<select>` populado dinamicamente (ex.: conexões compatíveis com uma capability), garanta que o mock de dados inclui uma opção com o valor que o teste vai selecionar. Descoberto em T25.
- **Pacotes do workspace com `main` apontando para `./src/index.ts`** (sem build) funcionam bem sob bundler (Vite) e sob runtime com transpilação on-the-fly (tsx), mas quebram sob `node` puro contra `dist/`. A API roda em produção via `tsx` no M0 (ambiente de desenvolvimento é o alvo declarado do milestone); virar isso num build real de produção fica para quando M0 sair de escopo dev.
- **O construtor de `Queue` do BullMQ chama `waitUntilReady()` internamente e força uma conexão de verdade ao Redis, ignorando `lazyConnect: true` da conexão ioredis que ele recebe.** `lazyConnect` só adia o handshake de uma conexão *crua*; assim que ela vira `connection` de um `Queue`, o próprio BullMQ dispara o `connect()` na hora da construção. Isso quebrou silenciosamente todo teste e2e existente quando o `ExecutionModule` (T6) passou a ser importado por `AppModule.register` em todo boot do papel `api`: cada teste que nunca chamava `/runs` mesmo assim tentava conectar num `REDIS_URL` fake (`redis://localhost:6379`, sem nada ouvindo), produzindo `unhandled rejection` (`Connection is closed`) e derrubando o `pnpm check` com exit code 1 mesmo com os 62 testes e2e passando. Corrigido criando a `Queue` (e a conexão por trás dela) só dentro do primeiro `enqueue()` real, memoizada (`RunQueueClient` em `apps/api/src/execution/queue.ts`) — nunca no registro do módulo. Lição geral: um provider Nest que "só cria o objeto" pode estar escondendo I/O de rede que o próprio construtor da lib dispara. Descoberto na T6.
- **A lição do `kek-rotate` (T8 do M1) se repetiu no `claimDueSchedules` (T3 do M2), mesma causa-raiz.** Qualquer repositório que varre todo tenant (não apenas o do contexto atual) acumula sobra entre testes que não compartilham tenant — isolar por `tenantId` não basta. `claimDueSchedules` reivindicava um `schedule` deixado por um teste anterior porque `next_run_at` daquele teste já tinha ficado no passado. Corrigido truncando `schedules` pela conexão de owner (não pelo pool de app, que não tem `TRUNCATE`) em `afterEach`. Lição geral: teste de repositório "cross-tenant" precisa de truncamento, teste de repositório "por tenant" não.

## Ideias adiadas

- Catálogo de conectores MCP dirigido por manifesto, sem deploy
- Banco dedicado por tenant para planos com exigência de isolamento físico
- Limites de gasto por tenant sobre a contabilidade de custo já coletada
- ~~Onboarding self-service para novos tenants~~ — entrou no escopo pelo PRD (IAM-001), milestone M6
- Keycloak (ou outro provedor de identidade) para login de usuário no painel, se um tenant quiser entrar com a conta corporativa — avaliado em 2026-09-06 e descartado para custódia de credencial de conector, que é problema de credencial de máquina, não de identidade de pessoa
- Swagger/OpenAPI para documentar a API — pedido pelo usuário em 2026-09-06. Sem milestone definido; entra quando a superfície de rotas do M1 estiver mais estável (depois da US2/US3), para não documentar rota que ainda vai mudar de forma
- Agente local de desktop para `file-storage` — pedido pelo usuário em 2026-09-07. Não substitui o painel web nem o modelo multitenant: é um extra opcional que o escritório instala na própria máquina, com acesso direto à pasta sincronizada (OneDrive/Drive já baixados localmente), evitando a API do fornecedor de nuvem. O usuário continua com acesso normal ao SaaS. Cabe como um adapter alternativo de `file-storage` no M3 (ao lado de `onedrive`/`google-drive`/`platform-upload`) — mas evitar de vender rótulo pesado: o "agente" precisa de um jeito de falar com o backend (upload por API, provavelmente), o que é escopo de design ainda não feito
- Mensageria: manter as três vias abertas, não escolher uma só — pedido pelo usuário em 2026-09-07. WhatsApp Cloud API oficial (já no M3), WhatsApp via bridge não-oficial tipo Baileys (grátis, risco de banimento — avisado ao usuário), e Telegram Bot API (grátis, sem risco de bloqueio, adoção menor no Brasil). Cada uma pode virar um `ConnectorDefinition` próprio com a mesma capability `messaging` — o agente escolhe qual bindar, sem mudar o modelo. Falta decidir prioridade de implementação quando o M3 chegar
